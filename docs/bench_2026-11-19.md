# VLM benchmark 1 (2026-11-19)

Set: `python -m vlmbaseline.bench.build_set data/library_merged data/lab_03` (seed 0, up to 4 objects per label,
best keyframe view; 129 views, 23 excluded by eye where the export box / label was wrong -> 106 scored; 40 scene questions).
Run: `python -m vlmbaseline.bench.run <model>` (bitsandbytes 4-bit nf4, greedy, thinking off), score: `python -m vlmbaseline.bench.score`.
GPU RTX 3080 Ti Laptop 16 GB.

- recog: red box on the keyframe -> English name, correct if it matches the reviewed label or a synonym / parent class.
- describe: Korean JSON (name, colour, material, state, uses); all three always return valid JSON in Korean. Content not scored.
- scene QA: object table (symbol, label, centre, size) as text + Korean question; counts, nearest, distance, largest / highest.

Findings
- Recognition: Qwen3.5-9B best (74%), Molmo2-8B 65%, Gemma-4-12B 55% (Gemma often names a different object than the boxed one).
- Common misses: orange cone-shaped sign stands ("orange cone"), small wall items (sticky notes, image signs, screens).
- Scene QA from a text table is poor for all (22-28%; distances ~0-8%): spatial facts must come from code over the graph
  (counting, distances, nearest, paths), with the VLM choosing the query and phrasing the answer.
- Speed and memory are fine for offline augmentation: 0.4-0.8 s per name, 2.3-3.5 s per description, 7-9.4 GB.

## Bench 5: guidance from the user's pose (2026-11-20)

The user's position and heading (x, y, yaw) can be given to the agent (`Agent.ask(q, pose=...)`); keyframe camera
poses stand in for the user here (8 per scene). Two tools exist only then:

- `guide_me(label | goal)`: nearest object by walking distance; turn-by-turn steps relative to the heading
  (직진 / 왼쪽·오른쪽으로 비스듬히 / 돌기 / 뒤로 돌기, walk m, up to 2 objects passed per step with their side),
  where the goal is now and at arrival. The place path is simplified (Douglas-Peucker 0.6 m, legs < 0.8 m and bends
  < 40° removed) so a corridor is one leg.
- `around_me(label, side)`: objects within 4 m with direction (앞, 왼쪽 앞, ..., 뒤), clock direction and distance;
  `side` filters in code.

Left / right is checked against the cameras: objects in view project to the image side that matches the computed
direction in 13521 / 13521 cases (`tests/test_nav.py`).

Agent guards: route / guide_to only start from an object symbol the user named (otherwise the tool returns an error
telling the model to ask where the user is); a guidance answer without the goal symbol is sent back once.

| Test (Qwen3.5-9B, 4-bit) | Before guards | After |
|---|---|---|
| '여기서 가장 가까운 X까지 어떻게 가?' (goal, first turn, guide_me used) | 14/16 | 15/16 (the miss: '안내판' taken as `sign`, a correct route to the nearest sign; the set expects `sign stand`) |
| '내 앞 / 왼쪽 / 오른쪽에 뭐가 있어?' (first object cited is on that side) | 9/11 | 11/11 |
| same guidance question with no pose | 0/4 (invented a start object) | 4/4 ask where the user is (scorer fixed afterwards to not count the blocked call) |

| bench 4 unanswerable again | 15/16 | 15/16 |

## Bench 6: areas (2026-11-20)

The export has one room per scene, so the floor is split in code into walkable areas (`spatial/areas.py`: geodesic
farthest-point seeds 7 m apart, geodesic Voronoi over the place graph, areas under 12 places merged; every area is
connected, `tests/test_areas.py`): library 9 areas, lab_03 13. The VLM names each area from 3 keyframes taken inside
it facing different ways, the object list, and the area shape measured in code (floor area, longest walk, mean
width, 'narrow and long' when width < 3 m) (`augment/describe_areas.py` -> `areas_vlm.json`, `area_views/`).
Without the shape hint and a 'feature + kind' naming rule the model named areas after one object ('문', '분리벽')
and called a curved corridor a reading space; with them: 원형 복도, 엘리베이터 앞, 화살표 표지판이 있는 복도,
원형 유리문 로비, 창가 휴게 공간, 컴퓨터 열람 공간 ... (22 / 22 parsed).

Tools: `areas(query)` (two-character overlap, common words like 공간 ignored), `area_info`, `where_am_i`,
`guide_me(area=)`, `guide_to(start, area=)`; guidance steps say which area they enter (`into_area`); `object_info`
gives the object's area. Guards: an area name that fits several areas equally ('열람 공간') is an error listing
them, not a random pick; when the question contains an area name and guidance went elsewhere (the model took
'화이트보드 있는 복도' for the whiteboard), the model is sent back once. `write_dsg` puts `vlm_area` on place nodes
and `metadata.vlm.areas` on the graph (spark_dsg loads it).

## Bench 7: follow-up questions (2026-11-20)

`Agent.ask(question, pose, history=[{q, a}, ...])` gives the model the last 3 turns as plain text (not their tool
calls). When the question points back ('거기', '그거', '그 옆', '다른 거' ...), the object symbols of the answer before
count as said by the user (so '거기서 Y까지' may start a route there) and the area named in the question before counts
as asked; without pointing back the start-object guard is unchanged. Tool results go to the model with area ids
removed where the area has a name (answers said '1번 구역'). New guards, each once: a route was asked but only
lookups ran (the model answered '가장 가까운 Y' with a straight-line distance) -> call guide_me / route / guide_to;
'다른 거는?' answered without another object of the same kind -> name one with its symbol; an answer ending in a
promise ('안내해 드리겠습니다') -> go on. The web page keeps the conversation (chat log, '새 대화' button).

`spatial/bench_dialog.py`: two-turn dialogues, 3 per kind and scene, scored from the tool calls of the second turn.

## Bench 8: guidance while walking (2026-11-20)

`spatial/follow.py` `Follower(idx, goal= | label= | area=)`: `start(pose)` plans the route, `update(pose)` (about
0.15 ms, no model) returns short Korean announcements: the first leg (merged with the next turn when the first
corner is within ~2.5 m), 'N m 앞에서 <turn>' when a corner is within 6 m, the turn and the next leg at 2 m, '반대
방향으로 가고 있습니다' after a few poses walking against the route, a new route after leaving it, and arrival
with the side of the goal. Progress along the route only moves forward (the lab_03 ring corridor). Leaving the
route needs both: more than 2.5 m from the route line and the walk to the goal (place graph) 3 m longer than the
best so far (or 6 m longer than what is left of the plan), two poses in a row. Korean particles are chosen in code
(`벤치(O223)는`, `원형 복도로`, `ETRI 열람 공간으로`) and labels are said in Korean (`spatial/names.py`).

`spatial/bench_follow.py` replays the recorded keyframe trajectories (a pose every ~0.25 m) as a user walking:
40 stretches per scene of 8-35 m that end within 1.5 m of an object (the goal), kept when the walk was close to the
planned route (walked <= 1.3 x planned + 2 m); after the recording the walker steps straight to the goal.

| Measure (80 walks) | Distance from the line only | + walk to the goal | Final |
|---|---|---|---|
| arrival announced, within 2.5 m of the goal | 80/80 | 72/80 (early: progress hit the end of the line 4-5 m beside it) | 80/80 (median 1.5 m) |
| 'left the route' while following (false alarms) | 40 in 21 walks (open library room: walking 2.5 m beside the straight line) | 1 | 1 (that walker took 8 m longer another way) |
| turn said, and the walker turned that way within 3 m | 41/46 | 40/44 | 34/36 (misses: slight turns cut across in an open room) |
| walking the recording backwards from the start: '반대 방향' or a new route within 6 m | 45/45 | 45/45 | 45/45 (median 2.1 m) |

The web page starts this after a guidance answer from the user's pose: moving the position on the map, or
'걸어 보기' (walks the route, 0.5 m every 0.5 s), gives the announcements in the chat; '음성' reads them with the
browser's Korean speech. A live pose stream (Hydra / RTAB-Map) only has to call `update` with each pose.

## Bench 9: live position (2026-11-20)

Guidance while walking needs the user's pose in the export's world frame while they walk. The odometry recorded
live drifts off the export: lab_03 keyframes vs its live odometry, 1.8 m median, 11 m at the end of the 143 m walk.
So the pose comes from RTAB-Map localization in a saved map of the place (`Mem/IncrementalMemory false`), and a
correction per map node brings it into the export's frame (`live/align.py`: C_k = world_T_body(k) * map_T_body(k)^-1,
node and keyframe matched by stamp; the bridge uses the node nearest to the pose whose id is closest to the last
matched node, i.e. the same pass). `live/bridge.py` (ROS 2) sends the pose at 2 Hz to the demo (`/api/live`), which
runs the Follower of the active guidance and queues its announcements for the page ('실시간 위치').

The saved map has to be one graph. The live database of lab_03 is in 25 pieces (a new map after every odometry
loss); localized in a piece not connected to the rest, the middle of the walk (140-255 s) drifted up to 6.4 m.
`scripts/build_map.sh` rebuilds it from the bag with the resets turned into uncertain links: 551 nodes, 1 map, 12 loop
closures; 370 nodes matched to export keyframes.

`scripts/localize_bag.sh` replays a recording at real speed as the live input; `live/bench_live.py` scores it.

|---|---|---|---|---|---|---|
| lab_03 in its own map, live database (25 pieces) | 617/617 * | 0.3 / 0.5 / 1.0 s | 0.06 / 2.79 / 6.40 m | 0.31 / 1.28 / 3.56 m | 3 | 40/40, 3 |
| lab_03 in the rebuilt map (one graph) | 616/617 | 0.3 / 0.5 / 4.3 s | 0.03 / 0.16 / 0.45 m (217 pairs, heading 0.2 / 1.6 deg) | 0.28 / 0.43 / 0.62 m | 2 | 40/40, 0 |

들어갑니다.' -> '엘리베이터 앞에 도착했습니다.' The page with '실시간 위치' shows the moving position, the route and the
remaining distance. `scripts/live_localize.sh` runs the same with the camera (realsense + rtabmap odometry +
localization + bridge, 848x480); not tried yet with a person walking.
